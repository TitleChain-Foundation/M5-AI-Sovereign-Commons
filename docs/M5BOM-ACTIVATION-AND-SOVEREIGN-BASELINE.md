# M5BOM activation and sovereign baseline

**Draft for Public Comment · 0.1.0**

The member promise is simple: activation establishes an attributable M5 context
and a portable baseline profile. It does not turn the person's own intelligence
runtime into a rental service.

## Activation sequence

1. Establish the accountable human and their selected BOM context using the
   existing identity, refusal/consent and account activation requirements.
2. Explain the local baseline, model license and device requirements. Resolve
   readiness honestly. Do not activate a paid provider to hide incompatibility.
3. Let the human select a compatible artifact and verify its exact source,
   revision and digest. Store private evidence locally, with protected refs.
4. Issue the portable [baseline profile](../schemas/m5-bom-sovereign-baseline.schema.json).
   Service price is $0, metering NONE, diagnostics OFF, network/payment not required.
5. Offer optional M5-Eve activation. Give each agent explicit capability,
   compartment, purpose, data-domain, jurisdiction, expiry and revocation limits.
6. Offer optional external compute with separate, scoped consent and budget.
   Choosing none must leave local inference usable.

## Two independent states

| State | Controls | Failure consequence |
| --- | --- | --- |
| Local baseline readiness | Compatible artifact, license and person-controlled hardware | Explain missing local prerequisites; no automatic purchase |
| Protected M5-Eve action eligibility | Principal, credentials, delegation, current namespace evidence, M5Canon and approvals | HOLD/DENY the protected action; preserve ordinary local inference |

The baseline profile references an account activation receipt; it is not itself
proof of identity or evidence that activation occurred. Identity verification
and credential issuance remain outside this public reference implementation.

Eve is the Jev chat experience identified for the first featured integration.
M5-Eve is that experience operating within M5's bounded account framework and
remains open to other providers. Laya is a first featured local decision
candidate. Neither product defines account authority. The repository's Vercel
Eve template reference is a separately attributed implementation reference;
product naming alone is not proof of common provenance or compatible APIs.

Milner preserves cognitive/account boundaries; Lenore supports deliberation.
Neither replaces deterministic policy or accountable approval. A provider swap
must pass compatibility, privacy and scope checks without changing who the
principal is or enlarging delegated authority.

## Acceptance checklist for an implementation

- Local inference works without a payment method or service meter.
- Disabling diagnostics, network and hosted integrations preserves inference.
- Account/session expiry blocks only functions needing current account authority.
- Revoked M5-Eve credentials prevent protected execution immediately on resolution.
- Export and deletion controls are usable; provider replacement is documented.
- Tier II/III cannot activate without current scoped consent and a spend ceiling.
- Infrastructure estimates are optional and separate from the $0 service price.

The [public tests](../tests/test_m5_bom_baseline.py) demonstrate contract behavior.
Hardware/runtime tests must be supplied by each deploying implementation.
See [M5-AIMARKET-001](../standards/M5-AIMARKET-001.md) for normative requirements.
